# 智能提醒 App — 用户反馈机制设计文档

> 版本：v1.0 | 2026-05-06
> 定位：基于用户行为和显性反馈的 AI 自适应推送系统

---

## 一、设计目标

1. **零感反馈优先**：80% 的反馈数据来自隐性行为，用户无需主动操作
2. **正循环建立**：用户反馈 → AI 更聪明 → 推送更精准 → 用户更愿意给反馈
3. **冷启动可用的默认策略**：新用户第一天就能获得不错的体验，无需先"喂养"数据
4. **渐进式个性化**：从通用推送到深度个性化，随使用时间逐步进化
5. **用户有掌控感**：随时可以看到"为什么推给我"、随时可以调整

### 2.2 隐性行为数据详解

这是整个反馈系统的基础，**不依赖用户主动操作，自动在后台收集**。

#### 通知到达后的处理方式

| 行为 | 采集方式 | 信号值 | 含义 |
|------|---------|--------|------|
| 3秒内划掉（Clear） | iOS UNNotificationAction | -0.3 | 烦扰/不相关 |
| 10秒内划掉 | iOS UNNotificationAction | -0.1 | 无感/不感兴趣 |
| 点击通知打开 App | UNUserNotificationCenter delegate | +0.5 | 有价值 |
| 点击后 App 停留 > 30秒 | App 内计时 | +0.6 | 高价值，采取了行动 |
| 点击后 App 停留 < 5秒 | App 内计时 | +0.1 | 点错了或内容不符预期 |
| 通知未被处理（到达10分钟后仍在锁屏） | 轮询检查 | -0.05 | 无感 |
| 通知被设为"稍后提醒"（Snooze） | 自定义 Action | +0.2 | 有用但时机不对 |
| 通知被标记为"已处理" | 自定义 Action | +0.4 | 有用且已行动 |

#### 信号值说明

- 信号值范围：**-1.0 到 +1.0**
- 负值 = 用户不喜欢，正值 = 用户喜欢
- 每个场景类别维护一个**加权移动平均分**，近期信号权重更高
- 当某类别分数持续低于 -0.1（连续7天），系统主动询问是否关闭

#### Live Activity 相关行为

| 行为 | 采集方式 | 信号值 |
|------|---------|--------|
| Live Activity 自然展示 > 2小时未关闭 | 活动生命周期 | +0.2（接受度高） |
| Live Activity 被 swipe 关闭 | ActivityDidDismiss | -0.2 |
| Live Activity 上点击进入 App | Deep Link 点击 | +0.4 |
| Live Activity 长按打开菜单 | Context Menu | 0（中性，探索行为） |
| Live Activity 上点击"换一个" | 自定义 Button | -0.1（当前内容不感兴趣） |
| Live Activity 上点击"不再显示" | 自定义 Button | -0.5（明确拒绝） |

### 2.3 显性微交互设计

#### 2.3.1 通知快速反馈按钮

iOS 支持在通知上添加 Category Action Button：

```
┌─────────────────────────────────────┐
│  🌧️ 今天下午有雨，出门记得带伞        │
│                                     │
│     [✓ 有用]        [✗ 不需要]       │
└─────────────────────────────────────┘
```

- **有用（+0.4）**：直接更新权重，无额外弹窗
- **不需要（-0.3）**：弹出轻量级二级菜单，**不超过 3 个选项**：

```
┌───────────────────────┐
│  不需要这条提醒？       │
│                       │
│  ○ 已经知道了          │
│  ○ 跟我没关系          │
│  ○ 以后都别推了        │
│                       │
│       [确认]           │
└───────────────────────┘
```

| 子选项 | 效果 | 说明 |
|--------|------|------|
| 已经知道了 | 本次 -0.2，不影响长期权重 | 信息重复，但不是不需要这类提醒 |
| 跟我没关系 | 该场景类别 -0.3，连续2次后暂停7天 | 场景不匹配用户画像 |
| 以后都别推了 | 该场景类别永久关闭，可在设置中恢复 | 明确拒绝，尊重用户意愿 |

**关键设计原则：二级菜单最多 3 个选项，超过 3 个用户会直接关掉。**

#### 2.3.2 Live Activity 交互

Live Activity 支持自定义 Button（iOS 16.1+）：

```
锁屏展示：
┌─────────────────────────────┐
│  🌧️  22°C 多云   下午有雨    │
│  记得带伞出门                │
│                             │
│  [换一个]    [👍]    [✕]     │
└─────────────────────────────┘
```

| 按钮 | 行为 |
|------|------|
| 换一个 | 立即从待推送队列取下一条展示，当前内容标记 -0.1 |
| 👍 | 标记 +0.3，同一内容24h内不重复推 |
| ✕ | 移除当前 Live Activity，标记 -0.3 |

长按 Live Activity 呼出 Context Menu：
```
┌─────────────────────┐
│  📌 固定到锁屏       │
│  ⚙️ 调整此类型偏好    │
│  🔇 暂停此类提醒7天   │
│  ❌ 不再显示此类      │
└─────────────────────┘
```

#### 2.3.3 "已处理"快捷操作

对可执行类提醒（吃药、喝水、拿快递、写周报），通知增加"已处理"按钮：

```
┌─────────────────────────────────────┐
│  💊 该吃降压药了                     │
│  每日 08:00                         │
│                                     │
│     [✅ 已吃]        [⏰ 30分钟后提醒]  │
└─────────────────────────────────────┘
```

| 操作 | 效果 |
|------|------|
| ✅ 已吃 | +0.4，记录完成时间，下次调整提醒时段 |
| ⏰ 稍后 | +0.2（认为有用但时机不对），30min后重新推送 |

## 三、AI 自适应推送算法

### 3.1 用户偏好模型

每个用户维护一个**场景权重向量**：

```
User_Preference = {
  weather:     0.85,   // 权重 0-1，1=非常喜欢
  time_routine: 0.60,
  calendar:    0.90,
  commute:     0.40,
  diet:        0.30,
  exercise:    0.15,   // 用户经常忽略运动提醒
  work:        0.75,
  life_service: 0.70,
  holiday:     0.55,
  mental:      0.50,
  family:      0.00,   // 用户未选择此标签
  pet:         0.00,
  growth:      0.35,
  finance:     0.65
}
```

### 3.2 权重更新规则

```
新权重 = 旧权重 × (1 - 学习率) + 新信号 × 学习率

默认学习率：
- 正反馈（用户点了"有用"）：α = 0.15
- 负反馈（用户点了"不需要"）：α = 0.20  // 负反馈响应更快
- 隐性行为（划掉/点击）：α = 0.05  // 隐性行为权重低，避免误判
- 用户标签选择：α = 0.80  // 主动设置的权重最高
```

**权重范围：0.00 ~ 1.00**
- 低于 0.10：自动暂停推送该类别，在设置中标记为"已暂停"
- 高于 0.80：可以适当提高推送频率（但不超过总频率限制）

### 3.3 时间衰减机制

用户的偏好会随时间变化，反馈数据需要有衰减：

```
信号时效权重：
  24h 内的反馈权重:  1.0
  3天内的反馈权重:   0.7
  7天内的反馈权重:   0.4
  14天内的反馈权重:  0.2
  30天以上的反馈权重: 0.05（几乎忽略）
```

这意味着：如果用户最近一周没有忽略运动提醒，之前积累的"不喜欢运动"信号会逐渐衰减，系统会重新尝试推送，试探偏好是否改变。

### 3.4 推送决策流程

```
┌──────────────────────┐
│  定时触发 / 事件触发   │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  收集当前上下文信号     │
│  - 当前时间 + 星期     │
│  - 天气数据           │
│  - 日历事件           │
│  - Health 数据        │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  匹配候选提醒集合       │
│  (所有满足触发条件的)   │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  用户偏好过滤          │
│  过滤掉权重 < 0.10 的  │
│  过滤掉已暂停的类别     │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  频率控制检查          │
│  - 当天已推数量 < 上限  │
│  - 同类间隔 > 30min    │
│  - 时段是否允许推送     │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  智能排序              │
│  Score = 场景匹配度    │
│        × 用户偏好权重  │
│        × 时效权重      │
│        × 多样性惩罚    │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  选择 Top 1-2 条      │
│  - 最高分的 → 通知推送 │
│  - 次高的 → Live Act. │
│  - 剩余 → 待推送队列   │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│  个性化文案生成（LLM） │
│  根据用户画像调整语气   │
│  和措辞               │
└──────────────────────┘
```

### 3.5 多样性机制

避免连续推同一类提醒：

```
连续推送惩罚：
- 最近 3 条都是同类 → 当前类别的得分 × 0.3
- 最近 2 条都是同类 → 当前类别的得分 × 0.6
- 最近 1 条是同类   → 当前类别的得分 × 0.85

跨天多样性：
- 每天确保至少覆盖 3 个不同的类别
- 如果今天只推了天气类，优先补充其他类别
```

### 3.6 惊喜机制（探索与利用平衡）

纯靠反馈推送会陷入"信息茧房"——用户永远只看到自己喜欢的类型。需要适度的"探索"：

```
惊喜推送规则：
- 每 10 条推送中，有 1-2 条是"不在用户标签内"的
- 只选择权重在 0.10-0.30 之间的"未明确拒绝"的类别
- 如果用户对惊喜推送给出正反馈 → 该类别权重 +0.15
- 如果用户对惊喜推送给出负反馈 → 该类别权重 -0.10，7天内不再惊喜推送该类
- "允许试推新类型提醒"可在设置中关闭
```

## 四、冷启动策略

新用户没有任何反馈数据，需要合理默认值确保首次体验：

### 4.1 默认推送策略

```
Day 1-3：保守期
- 只推送"高确定性"内容：天气提醒、时间问候
- 每天不超过 3 条
- 不推送任何需要用户画像的场景（家庭、宠物、财务等）

Day 4-7：试探期
- 引导用户选择兴趣标签（在首次点击了"有用"之后弹出）
- 开始推送日历相关提醒
- 每天不超过 5 条
- 根据前3天的隐性行为初步调整权重

Day 8+：正常运行期
- 根据偏好模型正常推送
- 每天不超过用户设定的上限（默认 8 条）
- 启动惊喜机制
```

### 4.2 默认兴趣权重

```
未选择标签时，默认全开但权重保守：
- 天气:      0.70  // 通用性最强
- 时间作息:   0.50
- 日历:      0.60
- 出行:      0.40
- 饮食:      0.30
- 运动:      0.30
- 工作:      0.40
- 生活服务:   0.40
- 节日:      0.50
- 心理关怀:   0.30
- 家庭:      0.00  // 默认关闭（涉及隐私推断）
- 宠物:      0.00  // 默认关闭
- 个人成长:   0.25
- 财务:      0.30
```

用户选择标签后，对应类别权重提升到 0.75，未选择的降为 0.05。

## 五、透明度与信任

### 5.1 "为什么推给我"机制

每条通知和 Live Activity 支持长按查看推理过程：

```
┌─────────────────────────────────────┐
│  为什么推送这条？                     │
│                                     │
│  📅 原因：                           │
│  · 今天有降雨预报（降水概率 85%）      │
│  · 你即将出门（日历中有通勤习惯）      │
│  · 你经常在 8 点左右查看手机          │
│                                     │
```

## 六、负面反馈处理

当用户出现"通知疲劳"信号时，系统需要有保护机制：

### 6.1 疲劳检测指标

| 指标 | 阈值 | 触发动作 |
|------|------|---------|
| 连续3天有用率 < 20% | 紧急 | 暂停推送48h，48h后以50%频率恢复 |
| 单日划掉率 > 70% | 警告 | 当天剩余推送取消 |
| 7天内未打开过 App | 警告 | 降低推送频率50%，推送一条"好久不见" |
| 主动关闭通知权限 | 严重 | 记录原因（如果用户有填写），发送一次挽留消息 |

### 6.2 挽留机制

```
当检测到用户可能流失时：

Day 1-2：降低频率（减半），推送质量最高的1-2条
Day 3-7：推送"好久不见"关怀消息，附带个性化洞察
Day 7+：推送一条"我们想你"，展示这段时间错过的最有价值的提醒
Day 14+：不再推送，只在 App 打开时展示新内容
Day 30+：彻底静默，除非用户重新打开 App
```

## 七、技术实现概要

### 7.1 数据存储

```
用户偏好表 (user_preferences)
├── user_id
├── category_weights (JSON)      // 14个类别的权重
├── time_preferences (JSON)      // 推送时段开关
├── daily_limit (int)            // 每日上限
├── learning_speed (enum)        // 学习速度
├── exploration_enabled (bool)   // 惊喜推送开关
├── updated_at (timestamp)

反馈记录表 (feedback_records)
├── record_id
├── user_id
├── notification_id
├── category (string)            // 场景类别
├── trigger_reason (string)      // 触发原因
├── delivery_time (timestamp)    // 推送时间
├── feedback_type (enum)         // implicit_dismiss / implicit_click / explicit_useful / explicit_not_needed / explicit_handled
├── feedback_sub_type (string)   // 子类型（如 "already_knew"）
├── signal_value (float)         // 信号值
├── time_to_action (int)         // 从推送到操作的毫秒数
├── dwell_time (int)             // App 内停留时间
└── created_at (timestamp)
```

### 7.2 权重更新流程

```
每次收到反馈
    → 查询该类别的当前权重
    → 计算时间衰减后的旧信号贡献
    → 应用学习率更新权重
    → 写入新的权重值
    → 如果权重低于 0.10，标记为"已暂停"
    → 如果权重从 <0.10 升到 >0.15，标记为"已恢复"
    → 触发偏好变更日志
```

### 7.3 推送调度

```
服务端定时任务（每5分钟执行一次）
    → 查询所有活跃用户
    → 对每个用户执行推送决策流程
    → 生成待推送队列
    → 通过 APNs 发送推送
    → 记录推送日志

事件触发推送（实时）
    → 天气突变（新天气预警到达）
    → 日历变更（新事件创建/修改/删除）
    → Health 数据更新
    → 直接执行推送决策，跳过定时调度
```
